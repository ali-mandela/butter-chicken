Autonomous Test Orchestration Agent · Architecture rev 3

The Orchestration Loop

Playwright already ships a Planner, a Generator and a Healer. The human is the glue between them. This architecture is about removing the glue — the decisions of when to plan, when to re-plan, when to generate, when to heal, and when to stop and ask.

"I've been using the Playwright agents, but still I am the one giving them context again and again. It is a lot of manual work."

Plate 01 · Input

One required input, three modes

A URL is the only thing the agent needs. Credentials are used when supplied. Everything else narrows the job — and their absence is itself an instruction.

ModeGivenWhat the suite aims atA "gap" means
1 · Sweep
the default		 --url (+ credentials if available) Full coverage. Every page, form and error state the explorer found deserves a scenario Anything discovered but untested
2 · Focused + --intent "focus on checkout and auth" Depth inside the stated scope Something inside that scope left untested. Flows outside it are deliberately untested, reported as such — never silently dropped
3 · Spec-led + --prd spec.md The requirements the document states A stated requirement with no scenario against it

The absence of a prompt is not the absence of instructions. It means "cover everything", and that is the hardest mode, not the easiest — it is also the one a judge will run first. Mode 1 is therefore the default the whole system is tuned for, and the coverage gate does the most work there because nothing else has narrowed the target.

Because the target changes per mode, the final report always states which mode it ran in. "3 gaps remaining" is meaningless otherwise.

Plate 02 · The loop

One URL in, a test suite and a quality report out

Nine stages and four decision points. The stages are the easy part — every one already exists in some tool. The decision points are the product.

Plate 03 · Implementation

A plain state machine, not a framework

The orchestrator is roughly two hundred lines of explicit Python. No LangChain, no LangGraph, no agent framework. That is a deliberate decision and worth defending.

Why no framework

  • It would hide what is being scored. Twenty percent of the grade is how intelligently the orchestrator handles coverage gaps, ambiguity and failure classification. In a framework those become chain internals; here each is a named function whose reasoning is printed.
  • The call volume does not justify it. A whole pipeline run is three to eight model calls. Frameworks earn their keep with heavy tool routing, not with a loop and four conditionals.
  • Dependency risk, already experienced. Every model identifier from training data returned 404 — the provider's free tier had fully rotated. Plain HTTP with an explicit model fallback chain survived that. A large dependency tree is one more thing to break the night before a deadline.
  • Explainability is a deliverable. The submission asks for the ability to explain trade-offs and architecture decisions. "We wrote a state machine and here is every transition" is a better answer than "the framework handled it".

The fair counterpoint: LangGraph is genuinely the closest fit, being a state-machine library with checkpointing and tracing. It was considered and rejected because it buys persistence and tracing we can hand-roll in an afternoon, at the cost of the transparency being graded.

# the entire control flow, in essence
state = OrchestratorState(url=url, credentials=creds, intent=intent, prd=prd)
while state.stage not in TERMINAL:
    decision = STEP[state.stage](state)     # pure, typed, testable
    state.ledger.append(decision)           # the report writes itself
    state.stage = decision.next_stage
    if state.over_budget(): state.escalate("budget exhausted")

Plate 04 · The decisions

What the orchestrator actually decides

This is the table to defend in a demo. Each row is a judgement a developer makes by hand today when driving Playwright's agents themselves.

GateQuestionEvidence it usesOutcomes
CoverageIs this plan worth building?Exploration digest versus the plan, scoped by input mode: every discovered form and error state (sweep), the stated intent (focused), or the document's requirements (spec-led)accept · re-plan with the gaps named · escalate
ValidationDid the generated flow compile, and does the emitted file run?Per-step selector resolution during the dry run, plus an import-and-collect check on the emitted pytest fileship flow · regenerate · drop flow and record the risk
TriageBroken script, or real bug?Failure kind, which tier resolved the step, whether an assertion or a locator failed, page state at failureheal · report as defect · flag as flaky
HealIs this repair safe to accept?Model confidence, semantic agreement on role and test id, heals already spentapply for this run and record · reject · escalate

The triage gate must never be wrong in one direction. Classifying a genuine application bug as a broken script means the agent repairs the test until it passes and the defect ships. That single failure mode destroys trust in this whole category of tool, so the bias is deliberately asymmetric: a failing assertion is always a candidate defect and is structurally ineligible for repair, even when a model is confident it could fix it. This is enforced in the type system, in the executor's cascade, and in the healer's first gate — three independent places, verified by test.

Healing during an autonomous run

The pipeline must not stop for a human, but a silent rewrite of a committed test is exactly what the research says destroys trust. The resolution: a heal is applied for the current run so the pipeline completes, recorded in the ledger with its confidence and reasoning, and surfaced in the report — while the committed test file changes only on explicit human approval afterwards. Autonomy during the run, review after it.

Plate 05 · Contracts

Three sub-agents, one meta-agent, and a crawler

The brief names three sub-agents. The Explorer sits below them as a deterministic tool rather than a fourth agent — it gathers evidence so the agents that cost money have something concrete to reason about.

Total for a full pipeline run: roughly 3 to 8 model calls for an entire suite — one plan, one or two critiques, and a handful of heals. Everything else, including all execution and all re-runs, is free. That is what makes the loop affordable enough to be genuinely autonomous rather than something you supervise because of the bill.

What the Generator emits

A runnable pytest file per flow, using Playwright's sync API, with credentials read from the environment rather than baked in. The validation gate then imports and collects the file to prove it is genuinely executable — closing the obvious objection that a JSON definition plus a bespoke runner is not an "executable test file".

# tests/generated/test_checkout_flow.py  (emitted by the Generator)
import os
from playwright.sync_api import Page, expect

def test_checkout_with_one_item(page: Page):
    page.goto("https://app.example.com")
    page.locator('[data-test="username"]').fill(os.environ["AIVAR_USERNAME"])
    page.locator('[data-test="password"]').fill(os.environ["AIVAR_PASSWORD"])
    page.get_by_role("button", name="Login").click()
    page.get_by_role("button", name="Add to cart").first.click()
    expect(page.locator('[data-test="cart-badge"]')).to_have_text("1")

Plate 06 · Bounds

The numbers that keep it finite

Every one is printed in the report. An agent whose limits are invisible is not trustworthy; an agent with no limits is not deployable.

GuardrailDefaultWhat it prevents
max_replans2Re-planning forever chasing perfect coverage
max_regenerations1Rebuilding a flow the application simply does not support
max_heals_per_run3A cascade of repairs quietly rewriting a whole suite
min_heal_confidence0.5Accepting a weak guess as a match
require_semantic_matchtrueRepairing onto a similar-looking but wrong element
heal_assertionsfalseMasking a real defect. Not configurable, by design
max_explore_pages8An unbounded crawl on a large application
max_flows6A plan too large to generate inside the demo budget
max_cost_per_run$0.50Silent budget drift as the suite grows
max_pipeline_seconds300A run nobody can sit through

Tuned so a default sweep completes in roughly three to five minutes — long enough to be a real suite, short enough to show live.

Deliberately out of scope

Production deployment, CI/CD integration, cross-browser matrix testing, and exhaustive coverage of a production application are all excluded by the brief and are not designed for. Nothing in this architecture spends effort on them. All test behaviour is produced by the pipeline; no hand-written test script is part of the product.

The summary. The pieces are strong and the hard safety properties are structural rather than aspirational. What is missing is the thing the problem statement is named after — the loop that runs them without a person in between. Until that exists, this system is precisely the complaint the briefing opens with.
