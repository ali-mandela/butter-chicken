Reference architecture · v1

QA Agent Blueprint

One rule shapes everything below: the model runs once to write a test, then gets out of the way. Every CI run after that is ordinary deterministic code. The model comes back only when a selector goes missing — never when an assertion fails.

DeterministicNo model call. Free, fast, runs on every build.
InferenceCosts money and seconds. Should be rare.
Never healsHard stop. The system may not rewrite this.
Human-ownedA person approves before it takes effect.

Plate 01 · The whole system

Three phases around one artifact

Most people picture a QA agent as a loop that thinks on every run. That design is roughly 1500× more expensive and non-reproducible. The working shape is three separate phases that meet at a single file.

Why not one clever loop? A per-step agent re-derives the page every run, so cost scales with steps × runs and no two runs are identical. Compiling once collapses that to a fixed cost paid at authoring time — measured at $0.002–$0.092 per compile versus $15–150 for the equivalent loop, with cached steps adding about 52ms over raw Playwright.

How one step finds its element

This runs for every step of every test. Read it as a waterfall: each tier is tried only because the one above it missed, and each tier costs more than the last.

Plate 03 · Failure handling

Four failures that must not be confused

This is the plate that separates a serious system from a demo. "The test failed" is four different events, and treating them alike is exactly how self-healing earns its bad reputation.

The one rule to never break: a failing assertion is a candidate bug, not a candidate repair. Locator drift may be healed. Behaviour may not.

Plate 04 · The design half

Order the checks by what they're anchored to

"Design intelligence" is reliable in exact proportion to how much external specification it checks against. That single idea sorts every possible check into three columns — and tells you what to build first.

Plate 07 · Build order

What to build, in sequence

Each stage is useful on its own and testable before the next begins. Resist building the healing loop early — it is the most interesting part and the least useful without the parts beneath it.

  1. Deterministic executor firstHand-write one compiled test as JSON — selectors and assertions — and an executor that runs it with Playwright. No model anywhere. You now have something real that passes and fails honestly.
  2. The resolution cascade, tiers 0 and 1Add cache lookup and accessibility-tree heuristics. Still no model. Most steps should already resolve; where they don't, you have learned what the model will need to handle.
  3. The plannerOne model call turning plain English into a step list, plus a dry run that verifies every selector resolves before anything is written to disk. This is the authoring phase, complete.
  4. Failure classificationImplement Plate 03 before implementing healing. Four distinct failure types, four distinct report lines. Assertion failures marked un-healable in the type system, not in a comment.
  5. Tier 2 and the heal loopModel re-ranking over a shortlist, the confidence and semantic gates, the heal cap, and the quarantine file. Nothing writes to the compiled test without approval.
  6. Spec-anchored design probesaxe-core, token linting, geometry checks. No baselines, no approval queue, immediate real findings. This is where the "design intelligence" half starts paying off.
  7. Visual regression, carefullyOnly once the above is stable, and budget most of the work on noise suppression — ignore regions, frozen animations, layout-level matching — rather than on the diff itself.
  8. The reportPer-step source, heal ledger, cost, design findings, and the approval queue. Everything a human needs to trust or distrust the run, on one page.

If you build only stages 1 through 4, you have a genuinely useful, fully deterministic QA agent with honest failure reporting. Everything after that is improvement, not foundation — which is the right way round.
